Work Credit RAG — Technical Documentation Report

Organization: شرکت اعتبارسنجی ایران (Iranian Credit Scoring Company)
Platform: Work Credit RAG Phase 1
Document date: 2026-11-09
Language: English (technical)
Repository: AliNikkhah2001/Work_Credit-RAG_Phase1 (umbrella) with submodules Work_RAG-KB, Work_RAG-Orchestrator, Work_RAG-Guardrails, Work_RAG-Server-Setup, ICS_ChatBot_agent-state

Document purpose

This report explains how the self-hosted Persian conversational RAG platform is structured, how a user request becomes a grounded answer, and how each major module contributes to retrieval, orchestration, model serving, safety, and observability. The prose is synthesized from the cloned codebase and measured artifacts; it is not a paste of repository READMEs.

Scope and version pins

The narrative reflects the November 2026 laptop clone of main tips (parent 9688549, KB 1af9772, orchestrator a3fb01e, guardrails bad5c84, server-setup f737c3d). Known tip gaps—such as KB dense encode via hasattr(dense, "model") and a missing /search/supplement route—are called out where they affect behavior.

Audience

Platform engineers, MLOps operators, and technical reviewers who need an end-to-end map before changing a submodule or deploying on Vast.ai / H200.

Executive summary and module overview

Section summary

Work Credit RAG is a Persian-first, self-hosted conversational system that answers credit-reporting questions using hybrid retrieval over an ICS knowledge base, a LangGraph orchestrator, and a fail-closed guardrails gateway in front of Gemma. Production code lives in Git submodules; the umbrella repository owns pins, contracts, evaluation, and host startup scripts.

Why the platform exists

Customers of شرکت اعتبارسنجی ایران ask about credit reports, cheque history, facilities for natural and legal persons, and related company knowledge. The product goal is to answer in natural Persian, stay inside policy, cite retrieved evidence, and run on owned GPU hosts without depending on a public LLM API for generation.

The MVP path is deliberately narrow: Open WebUI (:13000) talks to the orchestrator OpenAI-compatible API (:8100). The orchestrator validates input through guardrails (:8200), retrieves from the knowledge base (:8000), builds a bounded prompt, generates through the same guardrails service against Gemma (:18000 on Vast, or Manager :9000 on H200), and returns citations. Traces land in Langfuse (:3001) or a JSONL fallback collector (:3000).

Hosts in production practice

Two deployment shapes coexist. On Vast.ai (documented RTX 3090 instance), the stack runs as host virtualenvs—Docker is unavailable in the unprivileged container—and Gemma is a local llama-server bound to loopback :18000. On the H200 lab host, an LLM inference manager on :9000 load-balances llama.cpp backends and an optional TensorRT-LLM champion, while Redis, pgvector, and WebUI often sit in a Docker data plane. Both shapes share the same application modules; only process supervision and model gateway differ.

Design principles inferred from code

  1. Deterministic routing before generation — greetings and subspace specifications short-circuit; questions retrieve.
  2. Fail closed on safety errors — timeouts and empty judge outcomes refuse rather than pass through.
  3. Context is a hard budget — Triton/llama windows of 8192 tokens force chunk and entity trimming.
  4. Localhost HTTP bypasses corporate proxy — httpx uses trust_env=False throughout.
  5. Observability is multi-store — timings in responses, Langfuse spans, SQLite/JSONL for dashboards.

Request flow (detailed)

Figure 4. Sticky filtered RAG — detailed sequence. After start_trace, the orchestrator calls guardrails input check. Classification routes greetings and specifications away from retrieval. End-to-end walkthrough with code anchors

  1. Ingress — WebUI uses OPENAI_API_BASE_URL=http://127.0.0.1:8100/v1. Sticky threads rely on X-Request-ID / request_id (required in LangGraph Studio runs).
  2. Validate — nodes/validate_input.py calls Guardrails POST /v1/rails/check with stage=input. Blocks set blocked and route to format_refusal.
  3. Classify — nodes/classify.py labels greeting, specification, or question. Specifications lock subspace language for later filter_path.
  4. Retrieve — nodes/retrieve.py may rewrite coreference, apply sticky subspace decay, search KB, merge RRF/CE sets, fire entity tools, and evaluate evidence scores. Low evidence can refuse or broaden.
  5. Clarify or build — Ambiguous multi-subspace queries may ask a clarifying question via generate_clarification. Otherwise build_context.py assembles Persian system instructions, up to 20 chunks (MAX_CHUNKS), history (possibly compacted), and trimmed entity JSON.
  6. Generate — guarded_generate never talks to Gemma directly; Guardrails proxies upstream with cleanup of leaked special tokens.
  7. Format — Citations and finish reasons are shaped for the OpenAI response schema; audit/timing attach for non-stream responses.

Knowledge Base deep dive

Section summary. The Work Credit RAG Knowledge Base (components/knowledgebase, kb-manager) is the retrieval substrate for Persian credit-scoring Q&A: it turns heterogeneous source files into versioned chunks and entity supplements, then answers hybrid search requests with measurable stage latency. This section walks the ingest path (parsers → Persian preprocess → semantic chunking → EntityList), the live retrieval stack (tantivy BM25 + MiniLM dense + RRF k=60 + BGE-m3 rerank), Redis caching, subspace filters, observed IR quality, and the tip gaps that still affect orchestrator integration.

Purpose in the platform

The KB is neither a chat model nor a policy layer. Its contract is stricter: given a Persian (or mixed) query and optional subspace hint, return ranked chunk evidence with timing and citation metadata. The orchestrator (:8100) calls POST /search/api after input rails; build_context then packs hits for guarded generation. The service listens on :8000, persists via SQLAlchemy into Postgres + pgvector (SQLite fallback), and exposes FastAPI routes for search, pipeline, and metrics. Correctness is IR-first—Hit@k, MRR, nDCG—plus stage_ms so regressions surface as a quality cliff or a named-stage latency spike.

Ingest pipeline

Figure — High-level ingest. Source trees under kb-source enter one pipeline orchestrator that fans into durable stores: document/chunk tables (with dense embeddings) and a parallel EntityList table for structured supplements that must not be flattened into ordinary prose chunks. Ingest is a write-path concern separate from hybrid read; rebuilds or incremental updates produce a coherent snapshot for search consumers.

Coordination lives in components/knowledgebase/kb-manager/kb_manager/pipeline/orchestrator.py. PipelineOrchestrator selects a parser by extension (parsers/registry), runs PreprocessingPipeline for Persian hygiene (digit/character normalization, punctuation cleanup), then chunks with SemanticChunker and embeds via the sentence-transformer embedder. Folder hierarchy under kb-source becomes domain / category metadata—the later substrate for filter_path and sticky subspaces.

Figure — Ingest detail. The per-file loop is parse → preprocess → content-hash skip/update → semantic chunk → embed → store, with an early branch for supplementary Excel lists. Annex/list paths bypass normal chunking into EntityList rows; synonym/glossary annexes feed BM25 synonym resources instead of polluting the chunk corpus. Embedder wiring on that branch fills description_embedding for semantic routing—if the orchestrator is built without an embedder, those vectors stay empty and entity injection silently degrades.

SemanticChunker (kb_manager/chunker/semantic.py) prefers meaning-preserving units: tabular schemas become row-aware chunks with Persian field labels; narrative docs split on structure and normalized question text. Near-duplicate normalized questions are deduped so BM25 is not rewarded for FAQ clones.

EntityList model

Structured supplements are first-class in components/knowledgebase/kb-manager/kb_manager/models/database.py:

  • EntityList.list_name — human title used as the retrieval key surface
  • description / description_embedding — short Persian description plus JSON embedding for cosine matching
  • content_json — sheet/row payload kept intact for later injection into context

This design keeps bank-name tables, code maps, and similar annexes queryable as units instead of scattering cells across MiniLM space where short keys underperform.

Retrieval pipeline

Figure — High-level retrieval. A request hits Redis first (keyed on normalized query, top_k, optional keyword boost, and filter_path). Hits short-circuit the heavy path; misses run hybrid retrieve and write back with TTL 600 s. The coarse view explains why warm production traffic can look far faster than a cold micro-benchmark even when the ranker code path is unchanged.

The authoritative implementation is components/knowledgebase/kb-manager/kb_manager/web/routes/search.py. search_knowledge_base builds (or reuses) in-memory indexes and runs:

  1. Sparse leg — Rust tantivy BM25 (tantivy_bm25.py), Persian-aware tokenization with character 3-grams so short keyword queries still overlap.
  2. Dense leg — DenseSemanticIndex in dense.py over paraphrase-multilingual-MiniLM-L12-v2 (384-d), with vectors served from pgvector HNSW when configured. Encoding goes through _encode / _ensure_model; the private _model is not a public attribute.
  3. Optional HyDE — when enabled, an extra dense leg contributes another ranked list.
  4. Fusion — Reciprocal Rank Fusion with constant k = 60 (rrf_score = 1 / (k + rank + 1)), merging sparse and dense ranks into a hybrid candidate pool.
  5. Rerank — cross-encoder BAAI/bge-reranker-v2-m3 over a large candidate pool (env KB_RERANKER_TOP_K, default 100), with optional RRF↔︎rerank score interpolation and BM25-leg guards so dense-only dominance cannot bury a strong keyword hit.

Figure — Retrieval detail. Stages that populate SearchSteps.stage_ms are named explicitly: bm25, dense, hyde, rrf, rerank, build_context, and total. The same timings feed metrics.record_stage_ms, so a 20 ms regression can be blamed on rerank GPU contention versus a BM25 rebuild. filter_path prunes chunk_data before ranking for a subspace token or slash-separated path, matching ingest folder-hierarchy tags—how sticky product/domain subspaces work without re-embedding the query.

Redis cache and filters

KB_REDIS_TTL defaults to 600 seconds. Keys are SHA-256 digests of the normalized query plus top_k, keyword boost, and filter_path, so subspace answers do not leak across domains. If Redis is down, an in-process memory cache with the same TTL keeps single-worker use viable; production still prefers Redis for shared warm results across workers.

Known tip gaps

Two tip hazards remain and should not be rediscovered during orchestrator work.

First, several search.py sites still gate entity encoding with hasattr(dense, "model") and dense.model is not None. DenseSemanticIndex keeps the SentenceTransformer on _model, so the check is always false: entity inject becomes a silent no-op even when dense search is healthy. Use dense._encode([...]) (or a helper that calls _ensure_model).

Second, the orchestrator expects POST /search/supplement ({query, threshold}, default ~0.4) to rank EntityList rows by embedding over list_name + description. That route is missing on tip; only an in-/search/api step-8 inject remains, and it is compromised by the same hasattr bug. Restoring the route and wiring embeddings through _encode is required for reliable entity supplements in production chat turns.

Deep dive: Orchestrator

Section summary. The Work Credit RAG orchestrator is the public OpenAI-compatible face of the platform (:8100). It does not embed documents or serve Gemma itself: a compiled LangGraph (RAGState) validates and classifies each turn, retrieves from the knowledge base with sticky subspace memory, optionally clarifies ambiguous credit domains, packs a char-budgeted prompt, and always generates through Guardrails. Sticky filter_path, per-subspace evidence floors, entity-list trimming, and history compaction keep Persian multi-turn chats inside the 8192-token upstream window while preserving citations for the WebUI.

Role in the request path

Upstream of the graph, Open WebUI (or any OpenAI client) posts to FastAPI create_app in components/orchestrator/src/work_rag_orchestrator/api.py. The API allocates a request_id, restores prior sticky_subspace from the LangGraph checkpointer when the conversation continues, and invokes the compiled graph. Downstream dependencies are only KB (KB_BASE_URL, default :8000) and Guardrails (GUARDRAILS_BASE_URL, default :8200). Configuration for thresholds, keyword boosts, and compaction lives in config.py; the typed carry bag for every node is RAGState in state.py.

A deliberate invariant of the user-facing path: the orchestrator never opens an HTTP session to Gemma. guarded_generate posts prompt_messages to Guardrails POST /v1/chat/completions; Guardrails alone dials the loopback LLM (llama-server or the H200 manager). Input rails also run during validate_input via /v1/rails/check. Utility compaction may call an internal OpenAI-compatible summarizer for rolling history, but that path is system-generated and separate from answer generation.

LangGraph topology

The deterministic graph is assembled in graph.py (create_graph / compile_graph with MemorySaver for MVP checkpointing):

  1. validate_input — extract the latest user query; call Guardrails input rails. If blocked, route to format_refusal and end.
  2. classify — bucket the turn as greeting, specification, or question. Greetings and product-spec answers short-circuit straight to format_response (no retrieval).
  3. Optional hybrid_classify — when hybrid_classifier_enabled is true, an SVM-first classifier may escalate low-confidence labels before retrieval; otherwise edges go directly to retrieve.
  4. retrieve — rewrite/coreference as needed, call KB hybrid search (and optional supplement), apply sticky or inferred subspace filters, entity inject, and evidence gates.
  5. should_clarify — conditional edge: if supplemental/injected entities exist, continue (dictionary hits short-circuit clarification). Else if needs_clarification, embedding ambiguity (when routed), or scattered ambiguous queries with no applied_subspace, branch to generate_clarification and end. Otherwise continue.
  6. build_context — number sources, compact history, enforce prompt_char_budget and MAX_CHUNKS.
  7. guarded_generate — Guardrails chat completion → answer (or content-filter refusal).
  8. format_response — OpenAI-shaped payload plus RAG citations and audit fields.

Sticky subspace, filters, and evidence

Credit knowledge is partitioned into Persian path labels (cheque report, facilities for natural/legal persons, general KB). filter_path on the request is authoritative: when present, retrieve scopes KnowledgebaseClient.retrieve(..., filter_path=...) and maps the path back to a subspace label for badges and thresholds. Separately, sticky_subspace persists across turns in checkpointed state without always forcing this turn’s filter—state.py keeps it distinct from applied_subspace so the scorer can decide keep versus switch. The API layer may re-inject sticky scope for generic follow-ups (pronouns, short “بله/بیشتر”) while sticky_decay_turns (default 3) drops stale stickiness after consecutive generic turns.

Per-subspace evidence floors (config.get_evidence_threshold) refuse hallucination when top hybrid/rerank scores are too weak: cheque is lenient (0.05), facilities_person 0.10, facilities_legal and general 0.15 (global fallback evidence_min_score=0.15). Keyword boosts on filtered KB calls bias BM25 harder for cheque Q&A (3.5) than narrative general prose (2.5). Weak filtered hits can trigger a single whole-KB retry (filter_path=None) audited as fallback_used.

Entity dictionaries (reason codes, shareholders, loan titles) arrive as injected_entities / supplemental. trim_supplemental keeps at most top-3 lists × 4 KB serialized JSON each, ranks rows by query-token hit count, and doubles weight for code-like tokens (Latin letters or digits such as sbd1) so exact codes outrank rows that only share the word «کد». Without this trim, a single reason-code sheet can exceed 100 KB and overflow the upstream context.

Context packing and compaction

build_context.py caps retrieval evidence at MAX_CHUNKS = 20, prefers lexical matches when truncating, and respects prompt_char_budget = 20000 characters for the full generation prompt (system + context + history + question + entity reserve). Persian can tokenize near ~3 chars/token; twenty thousand characters leave headroom inside an 8192-token Gemma window for the answer. When estimated tokens exceed compact_threshold_tokens (4500), rolling-summary compaction replaces older turns while keeping the newest compact_recent_turns verbatim; prior “not found” refusals are stripped so they do not poison a later successful retrieval.

6. Deep Dive: Server Setup & Model Serving

Section summary

Work Credit RAG runs on two deliberately different hosts: an unprivileged Vast.ai RTX 3090 used for integrated MVP bring-up, and a corporate H200 box (ai-gpu1) that owns production model serving. The Vast path boots application services from host virtualenvs via deploy/vast/start.sh and treats Gemma as an external llama-server on loopback :18000. The H200 path introduces the LLM Inference Manager on :9000 as an OpenAI-compatible gateway in front of a multi-backend fleet—llama.cpp Gemma replicas on 8080–8084, TensorRT-LLM champion traffic on :8010, and embedding workers on 8001–8003—while Redis, vector stores, and Open WebUI ride a Docker data plane. Corporate egress goes through Squid at 192.168.203.2:3128, which makes httpx trust_env=False on localhost calls a hard correctness requirement. Containerization is staged (compose.mvp.yml for privileged compose hosts; parent deploy/docker plus the server-setup cutover plan for H200). Capacity planning follows docs/plans/million-user-scale-plan.md: Kubernetes horizontal scale-out versus saturating 2×H200 scale-up. Measured generation throughput on H200 (history 013) shows TensorRT-LLM BF16 continuous batching reaching ~3874 aggregate tok/s at concurrency 128 versus a flat ~58 tok/s llama.cpp Q4 single-slot path—about 67× aggregate under the same Persian decode workload.

Dual hosts: Vast MVP versus H200 production

The Vast instance (documented against instance 50713720, 1× RTX 3090, ~24 GB VRAM) cannot run Docker: the container is unprivileged, so unshare/iptables fail and compose.mvp.yml is reserved for privileged or local compose hosts. Startup order is postgres → Gemma → KB :8000 → guardrails :8200 → tracing collector :3000 → orchestrator :8100 → Open WebUI :13000, driven by bash deploy/vast/start.sh and torn down with port-scoped deploy/vast/stop.sh (never pkill python). Gemma stays bound to 127.0.0.1:18000 with --ctx-size 8192, --no-mmproj, --jinja, and chat_template_kwargs that disable thinking tokens; guardrails point UPSTREAM_LLM_BASE_URL at that loopback OpenAI surface. HF caches must set both HF_HOME and HF_HUB_CACHE (typically /tmp/hf_clean) or hub 1.x resolves an empty phantom tree. Public reachability is SSH tunnels only; NAT port remapping after creation is unavailable.

The H200 host is the opposite operational model: Docker is available for the data plane, Jenkins can act as root, and GPU memory (2× H200 NVL) supports concurrent backends. Model control plane is the manager on :9000. Chat backends include five llama.cpp Gemma instances (8080–8084), optional Qwen on :8090, and the TensorRT-LLM champion on :8010. Embedding microservices expose e5 / BGE / MiniLM-style endpoints on 8001–8003 for KB and offline tooling. Orchestrator and guardrails still speak OpenAI JSON, but production generation is intended to go Manager → champion (with automatic fallback into the llama.cpp pool if :8010 is unhealthy). Manager OpenAI gateway and Squid discipline

components/server-setup/llm_inference_manager/app.py exposes /v1/chat/completions, /v1/completions, /v1/models, /health, plus admin load/unload and Triton/TRT promote endpoints. Round-robin counters distribute load across replica URLs; SQLite (manager.db) records history and metrics. Every outbound call to localhost backends constructs httpx.AsyncClient(..., trust_env=False). That flag is not stylistic: the host shell exports HTTP_PROXY/HTTPS_PROXY toward Squid http://192.168.203.2:3128 for apt, pip, git, and Hugging Face. If httpx inherits those variables, loopback requests to :8010 or :8080 are sent to Squid, which cannot hairpin them, and health checks hang or fail opaque timeouts. The same rule appears in guardrails and observability clients; operators still need no_proxy/curl --noproxy '*' for manual probes. Promotion of gemma-4-31b to TRT is an admin action (POST /admin/triton/promote?...) that flips the gateway mapping without changing orchestrator env vars.

Containerization and cutover

Three layers coexist. Root compose.mvp.yml describes a privileged MVP: containerized postgres/pgvector, Redis, KB, guardrails, orchestrator, and WebUI, with Gemma remaining external on the host (host.docker.internal:18000). Parent deploy/docker/ holds compose variants (docker-compose.yml, GPU and Qdrant overlays, nginx) for hosts that can run the NVIDIA runtime. On H200, components/server-setup/docs/migration/containerization-report.md defines a zero-downtime cutover: build images first, validate each service on alternate ports, run E2E through WebUI against alt backends, then per-service swap host process → container on the same production port, with host venvs retained for rollback. Final port identity is frozen (8000, 8001–8003, 8080–8084, 8100, 8200, 9000, 13000, Redis 16379, postgres 5432, tracing 3000). Phases 1–3 never stop production traffic; only Phase 4 cutover changes listeners.

Scaling: million-user plan and measured decode throughput

docs/plans/million-user-scale-plan.md separates scale-out from scale-up. Scale-out places stateless FastAPI/orchestrator pods behind Kubernetes Ingress with HPA on CPU, GPU inference behind Triton/TensorRT replicas scaled by queue depth (KEDA), and a dedicated vector cluster (Qdrant) with read replicas—trading operational complexity for elastic concurrency (Figure 17). Scale-up keeps a single 2×H200 machine saturated: large in-RAM indexes, many Triton instance groups per GPU, and Gunicorn worker counts near core count, minimizing cross-node latency at the cost of vertical coupling (Figure 18). For Work Credit RAG’s Persian chat path, generation—not retrieval—dominates wall time, so inference batching efficiency dominates capacity math.

Figure 17 — Cloud-native scale-out. CPU tiers (orchestrator, guardrails, KB) scale independently of GPU inference tiers behind Ingress and HPA/KEDA. Semantic cache and hybrid vector search sit beside autoscaled Triton/TRT replicas so decode GPUs are not wasted on duplicate retrieval work. This is the elasticity path when concurrent Persian chat outgrows a single chassis.

Figure 18 — Bare-metal scale-up. One chassis, two H200s, shared-memory friendly batching. Prefer this when the model footprint fits and operational ownership stays on ai-gpu1.

History 013 (components/server-setup/docs/history/013_2026-10-13_trtllm_champion_concurrency.md) recorded a like-for-like Persian prompt (max_tokens=256) across concurrency. llama.cpp Q4 on the single-slot placeholder stayed ~58–59 aggregate tok/s at every concurrency (no continuous batching). TensorRT-LLM BF16 on :8010 scaled roughly linearly with in-flight requests: ~50 tok/s at conc 1, ~386 at 8, ~1385 at 32, and 3874.2 aggregate tok/s at conc 128 (~67.3× versus the flat Q4 baseline). Single-stream favors Q4 slightly (memory traffic); multi-user traffic favors TRT. Operators should size on sustained ~2.9k tok/s under power capping, not the first-burst 3.8k peak, and keep CUDA-graph batch sizes dense up to 128 so intermediate concurrencies do not fall off the graph cliff into eager decode.

Deep Dive: Guardrails & Security

Section summary

Guardrails (Work_RAG-Guardrails, port :8200) is the mandatory safety boundary between the LangGraph orchestrator and the Gemma inference plane. Every user turn is checked on the input stage before retrieval context is answered; every completed assistant reply is checked again on the output stage before it returns to WebUI. The service no longer embeds NVIDIA NeMo Guardrails. Runtime policy is a two-layer stack: fast deterministic detectors that emit evidence signals, then an adjudicating judge (gemma, mizan, or hybrid) that must allow or refuse. Judge timeout, empty verdict, or transport error fails closed—the request is refused rather than passed through. Production refusals are premade Persian category messages that never leak detector internals; Iranian PII in allowed answers is masked; secret markers hard-block.

Position in the request path

Figure 11 places Guardrails between Orchestrator :8100 and Gemma (:18000 on Vast llama-server, or Manager :9000 on H200). The orchestrator never calls the LLM directly: it posts rails/check for input and output stages, then chat/completions for guarded generation. The reply that reaches the user is either a masked safe completion or a category-scoped refusal.

Figure 11 — High-level placement. The orchestrator never dials Gemma directly: it posts rails/check for input and output stages, then chat/completions for guarded generation. Guardrails alone proxies to llama-server :18000 (Vast) or Manager :9000 (H200) and returns either a PII-masked safe completion or a category-scoped Persian refusal. The diagram is the safety contract for the rest of this section.

After NeMo: signals, judge, fail-closed

nemoguardrails was removed because its LangChain pin conflicted with the installed stack and initialization failed on every start. The replacement lives in components/guardrails/src/work_rag_guardrails/:

Module Role
service.py FastAPI app, /v1/rails/check, /v1/chat/completions, premade refusals, upstream proxy, history trim
signals.py Deterministic detectors → evidence list (injection, jailbreak, HurtLex hate, profanity, scope, PII)
judge.py adjudicate() — secret hard-block, policy judge backends, direct-LLM self-check, fail-closed

dashboard.py Zero-dependency RTL dashboard on the same :8200 process

collect_signals normalizes Persian text and runs pattern/list detectors. Those hits are helpers for the judge, not automatic blocks—except secret (sk-…, api_key, database_url, Bearer …), which adjudicate short-circuits to refuse. Domain keywords from the active policy feed a fast out-of-domain pre-check; missing policy or empty keyword lists fail closed into review.

Judge backend is selected with GUARD_JUDGE_BACKEND:

  • gemma — pinned-policy categories judged by Gemma; parse VERDICT / CATEGORY; empty or unparseable → refuse.
  • mizan — Mizan System-1 via Manager (/systemone) with calibrated safety / scope / severity questions.
  • hybrid — Mizan first; escalate to Gemma when confidence is low, severity is high, or hard signals fire (injection, jailbreak, secret, PII, hate, offense).

GUARD_JUDGE_MODE=on-signal (default) skips the LLM judge when the text is clean; always forces adjudication. A second-opinion direct-LLM yes/no self-check (env still named GUARD_NEMO_SELFCHECK for compatibility) remains fail-closed on error.

Figure 12 — Normalize → collect signals → domain scope → policy judge (Gemma / Mizan / hybrid) → direct-LLM self-check → allow or premade Persian refuse. Errors route to fail-closed refusal.

Endpoints and user-facing policy

POST /v1/rails/check accepts {stage, text, request_id} for input or output. The response carries allowed, action, category ids, and a reason string. In production mode (GUARD_RESPONSE_MODE), reason is a premade Persian message keyed by category—prompt injection, jailbreak, hate, offense, out-of-scope, PII, secret, policy—without exposing regex matches or judge traces. Output-stage hate/profanity refusals blame the answer (“پاسخ حاوی محتوای نامناسب است…”) rather than the user.

POST /v1/chat/completions is the OpenAI-compatible guarded gateway used by the orchestrator’s guarded_generate node. Flow:

  1. Extract the question slice from an augmented user message (Question: / سوال:), cap to the rails text limit.
  2. Input rails → refuse with finish_reason="content_filter" if blocked.
  3. Trim chat history to a Persian-aware char budget so upstream context (8192 tokens) is not overflowed.
  4. Call Gemma with chat_template_kwargs: {"enable_thinking": false} and strip leaked control tokens.
  5. Output rails → refuse or continue.
  6. If Iranian PII validators still match an allowed answer, events.mask_text replaces national-id / Sheba / mobile digit runs (and API-key-like spans) before return.

Health and readiness expose upstream reachability and policy version; the interactive dashboard aggregates masked JSONL events (block rate, categories, 24h timeline, sample viewer).

Upstream contract details

All outbound httpx.AsyncClient calls to :18000 / :9000 set trust_env=False. Without that flag, a host Squid HTTP_PROXY can hang loopback traffic and stall generation.

Upstream context overflow and other Gemma failures used to surface as pydantic validation crashes when the code emitted finish_reason="error" (not in the OpenAI-compatible literal). The gateway now maps timeout and overflow paths to finish_reason="length" with a short Persian retry hint—never an internal 500 and never a leaked token-budget body. Successful rails refusals use content_filter; clean answers use stop.

Known gaps

Streaming. When stream=true, input rails still run, then tokens are forwarded from upstream SSE (or chunked from a buffered JSON body). The live stream path does not reassemble the full assistant text for output rails or append a complete output-stage JSONL event the way non-streaming guarded_completion does. Operators should treat streaming as latency-first and keep production WebUI on buffered completions until output rails are applied post-stream.

Observability class unwired. observability.py defines a Phase-4 helper that would attach request_id, triggered rules, risk scores, and latency to responses, but nothing in service.py or judge.py imports it. Live telemetry today is the masked events JSONL plus the dashboard—not the richer risk-scorer envelope.

8.2 Knowledge-base stage_ms and Redis

Every successful POST /search/api response includes a stage_ms object written in kb_manager/web/routes/search.py as each leg finishes: BM25 (tantivy RAM index), dense MiniLM encode + HNSW/pgvector lookup, Reciprocal Rank Fusion (k=60), BGE-m3 cross-encoder rerank, and total. The same object is stored with the cached SearchSteps payload under Redis (KB_REDIS_TTL, default 600s) or an in-memory fallback when Redis is down; exact-cache hits typically return in 2–7 ms and never cache error responses. Operators can therefore diagnose “dense vs rerank” without attaching a profiler—jq '.stage_ms' on a warm curl is the day-to-day tool.

8.3 Orchestrator timings, AuditTrail, and ORCH_DEBUG

Graph nodes call record_timing(state, stage, elapsed_ms) (state.py) so retrieve, clarify, build_context, guarded_generate, format, and retry/broaden paths accumulate into state["stage_timing_ms"]. On the non-streaming OpenAI chat path, api.py builds a Pydantic AuditTrail that copies those timings together with retrieved chunks, guard signals, context preview, subspace ambiguity fields, and wall latency_ms. Setting ORCH_DEBUG=1 turns on app-level INFO logging (uvicorn alone would otherwise silence the package logger) and enables opt-in context diagnostics inside build_context so engineers can verify what actually reached Gemma without redeploying.

Streaming caveat. The SSE branch streams tokens from Guardrails → Gemma and finalizes citations/metadata, but it does not assemble the full AuditTrail save path used by the buffered branch. Traces still update, yet operators relying on audit-complete JSON for offline review will under-collect streaming traffic.

8.4 Langfuse v2 HTTP and host fallbacks

work_rag_orchestrator/tracing.py prefers direct HTTP to Langfuse v2: envelopes carry top-level id + ISO timestamp, and updates re-trace-create the same id (v2 has no trace-update). Posts are submitted on a small thread pool with short timeouts so tracing never blocks the request loop. When the real UI at :3001 is unavailable, the same path targets the parent components/tracing collector on :3000, which appends to /tmp/langfuse_traces.jsonl and exposes a minimal Langfuse-compatible ingestion + /observe timeline UI.

Separately, eval_store.py persists enriched pipeline cards to /tmp/observability.db (WAL SQLite, EVAL_DB_PATH) and mirrors them to /tmp/pipeline_traces.jsonl (TRACE_JSONL). The observability dashboard router under /api/observability is how Studio/WebUI-side tooling can push ratings and stage cards into that store.

8.5 Guard events, manager metrics, and retrieval DLQ

Guardrails write terminated/allowed decisions to /tmp/guard_events.jsonl (GUARD_EVENTS_FILE) with digit-run PII masking, and serve aggregates on the Persian dashboard at http://127.0.0.1:8200/dashboard. On the model plane, llm_inference_manager keeps session, message, and latency rows in manager.db and surfaces KB stage_ms breakdowns when a manager-side search probe is used. When filtered retrieval returns empty (or fails after fallbacks), orchestrator retrieve.py appends a record to /tmp/dlq_retrieval.jsonl so empty-hit regressions remain greppable after the fact.

8.6 Known gaps

Three instrumentation holes still matter in production tips:

  1. KB Prometheus record_* unwired. kb_manager/web/routes/metrics.py defines record_stage_ms, record_request_outcome, record_result_count, and record_cache_hit behind GET /metrics, but the live search pipeline never calls them—histograms stay empty while stage_ms in JSON remains the ground truth.
  2. retrieval_logs table has no writers. SQLAlchemy declares retrieval_logs in models/database.py, yet no ingest/search path inserts rows; historical analysis must use JSONL/bench artifacts instead.
  3. Streaming skips full audit save (see §8.3)—WebUI streaming users get citations without the rich AuditTrail payload non-streaming clients receive.

8.8 Optimizations that moved the numbers

  • RAM-first tantivy + HNSW. Rust tantivy BM25 (≈50 MB heap, RAMDirectory) and RAM-pinned dense/pgvector HNSW remove cold disk seeks from the hot path; startup pre-warm loads indexes and CUDA kernels before the first user query.
  • RRF then selective rerank. Fusion at k=60 keeps candidate quality high while the cross-encoder scores a bounded pool (GPU, pool 30)—cheap legs stay cheap.
  • Entity / context trim. Orchestrator supplemental injection is capped (top-3 × ~4 KB) and prompt_char_budget≈20k / MAX_CHUNKS=20 protect the Gemma 8192 context window from overflow (upstream overflow is surfaced as finish_reason=length, not a hard 500).
  • TRT champion serving. On H200, TensorRT-LLM Gemma remains the throughput champion versus llama.cpp Q4 for concurrent decode; Vast MVP still pin llama-server :18000 for the single-GPU box, but latency planning assumes generate cost scales with tokens and concurrency, not with KB stage_ms.
