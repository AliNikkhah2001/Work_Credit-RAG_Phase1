Architecture Overview

The Work Credit RAG platform follows a layered service-oriented architecture. User requests flow from a browser through Open WebUI to the Orchestrator, which coordinates retrieval from the Knowledgebase, safety validation through Guardrails, and generation via an LLM. All interactions are traced for observability.

Design principles: Self-hosted (no external model dependencies for generation), Persian-capable (language-specific safety and embedding), sticky conversation memory (X-Request-ID threading), and production-grade observability (traces, metrics, dashboards).

Key Components

Orchestrator (:8100)

LangGraph-based RAG graph that validates input, classifies queries, retrieves context, builds context, generates guarded answers, and formats responses. Uses MemorySaver for sticky conversation threads.

Knowledgebase (:8000)

Hybrid retrieval service with BM25 keyword search, dense semantic search, RRF fusion, cross-encoder reranking, and folder_hierarchy / filter_path scoping over 1123 chunks.

Guardrails (:8200)

Persian safety policy service with input/output rails, deterministic signal detection, LLM judge, and guarded generation through upstream Gemma.

LLM Manager (:9000)

OpenAI-compatible gateway in front of 11 llama.cpp backends with round-robin load balancing, session management, and model registry (H200 deployment).

Observability

Trace collector (:3000) with SQLite storage, Langfuse (:3001) full trace UI, and LangGraph Studio (:2024) for graph debugging.

Open WebUI (:13000)

Chat frontend (ICS Helper) with rag_trace_capture filter for sticky context capture and four user actions: rate, report, view, truth.

Caption: Request Flow — High-Level Black Box

  • User — The end user initiating a conversation.
  • WebUI — The chat frontend that receives the user message.
  • Orchestrator — The central service coordinating the RAG pipeline.
  • Knowledgebase — The document retrieval service.
  • Guardrails — The safety validation service.
  • LLM — The language model generating answers.
  • Observability — The tracing and monitoring infrastructure.
  • User → WebUI: Message — The user sends a message through the chat interface.
  • WebUI → Orchestrator: Request + request ID — The frontend forwards the user message with a unique request identifier for sticky tracking.
  • Orchestrator → Guardrails: Input safety check — The orchestrator validates the input for safety violations before processing.
  • Orchestrator → WebUI: Refusal — If the input is blocked, a refusal message is returned to the user.
  • Orchestrator → Knowledgebase: Retrieve context — If allowed, the orchestrator queries the knowledgebase for relevant documents.
  • Knowledgebase → Orchestrator: Results — Retrieved document chunks are returned to the orchestrator.
  • Orchestrator → Guardrails: Generate guarded answer — The orchestrator requests generation with safety guards applied.
  • Guardrails → LLM: LLM completion — Guardrails sends the generation request to the language model.
  • LLM → Guardrails: Answer — The language model returns a raw answer.
  • Guardrails → Orchestrator: Guarded answer — Guardrails returns the safety-checked answer.
  • Orchestrator → WebUI: Response with citations — The final answer with source citations is sent to the user.
  • Orchestrator → Observability: Trace — The full request trace is recorded for observability.

    Start --> Validate
    Validate -->|blocked| Refuse
    Validate -->|allowed| Classify
    Classify -->|greeting spec| Format
    Classify -->|question| Retrieve
    Retrieve -->|ambiguous| Clarify
    Retrieve -->|clear| Build
    Clarify --> End
    Build --> Generate
    Generate --> Format
    Refuse --> End
    Format --> End

Caption: Orchestrator LangGraph — High-Level Black Box

  • Start — Entry point of the LangGraph state graph when a request arrives.
  • Validate input — Checks the user input for safety violations and validity.
  • Classify query — Determines whether the query is a greeting, specification, or question.
  • Retrieve context — Fetches relevant documents from the knowledgebase.
  • Clarify if ambiguous — Asks the user for clarification when the query is unclear.
  • Build context — Assembles retrieved chunks into a context window for generation.
  • Guarded generate — Generates an answer with safety guardrails applied.
  • Format response — Formats the final answer with citations and metadata.
  • Format refusal — Formats a refusal message when input is blocked or no evidence is found.
  • End — Terminal node where the response is returned to the user.
  • Start → Validate — Every request begins with input validation.
  • Validate → blocked → Refuse — Blocked inputs go directly to refusal formatting.
  • Validate → allowed → Classify — Allowed inputs proceed to query classification.
  • Classify → greeting/spec → Format — Greetings and specifications bypass retrieval and go straight to formatting.
  • Classify → question → Retrieve — Questions proceed to context retrieval.
  • Retrieve → ambiguous → Clarify — Unclear queries trigger clarification before retrieval.
  • Retrieve → clear → Build — Clear queries proceed to context building.
  • Clarify → End — After clarification, the flow ends (user must re-ask).
  • Build → Generate — Built context is passed to the guarded generator.
  • Generate → Format — The generated answer is formatted for the user.
  • Refuse → End — Refusal messages terminate the flow.
  • Format → End — Formatted responses terminate the flow.
