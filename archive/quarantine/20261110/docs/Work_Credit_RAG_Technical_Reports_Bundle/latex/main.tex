\section{Executive summary and module
overview}\label{executive-summary-and-module-overview}

\subsection{Section summary}\label{section-summary}

Work Credit RAG is a \emph{Persian-first}, self-hosted conversational
system that answers credit-reporting questions using hybrid retrieval
over an ICS knowledge base, a LangGraph orchestrator, and a fail-closed
guardrails gateway in front of Gemma. Production code lives in Git
submodules; the umbrella repository owns pins, contracts, evaluation,
and host startup scripts.

\subsection{Why the platform exists}\label{why-the-platform-exists}

Customers of \textbf{شرکت اعتبارسنجی ایران} ask about credit reports,
cheque history, facilities for natural and legal persons, and related
company knowledge. The product goal is to answer in natural Persian,
stay inside policy, cite retrieved evidence, and run on owned GPU hosts
without depending on a public LLM API for generation.

The MVP path is deliberately narrow: Open WebUI (\texttt{:13000}) talks
to the orchestrator OpenAI-compatible API (\texttt{:8100}). The
orchestrator validates input through guardrails (\texttt{:8200}),
retrieves from the knowledge base (\texttt{:8000}), builds a bounded
prompt, generates through the same guardrails service against Gemma
(\texttt{:18000} on Vast, or Manager \texttt{:9000} on H200), and
returns citations. Traces land in Langfuse (\texttt{:3001}) or a JSONL
fallback collector (\texttt{:3000}).

\subsection{Hosts in production
practice}\label{hosts-in-production-practice}

Two deployment shapes coexist. On \textbf{Vast.ai} (documented RTX 3090
instance), the stack runs as host virtualenvs---Docker is unavailable in
the unprivileged container---and Gemma is a local \texttt{llama-server}
bound to loopback \texttt{:18000}. On the \textbf{H200} lab host, an LLM
inference manager on \texttt{:9000} load-balances llama.cpp backends and
an optional TensorRT-LLM champion, while Redis, pgvector, and WebUI
often sit in a Docker data plane. Both shapes share the same application
modules; only process supervision and model gateway differ.

\textbf{Figure 4. Sticky filtered RAG --- detailed sequence.} After

\subsection{End-to-end walkthrough with code
anchors}\label{end-to-end-walkthrough-with-code-anchors}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Ingress} --- WebUI uses
  \texttt{OPENAI\_API\_BASE\_URL=http://127.0.0.1:8100/v1}. Sticky
  threads rely on \texttt{X-Request-ID} / \texttt{request\_id} (required
  in LangGraph Studio runs).\\
\item
  \textbf{Validate} --- \texttt{nodes/validate\_input.py} calls
  Guardrails \texttt{POST\ /v1/rails/check} with \texttt{stage=input}.
  Blocks set \texttt{blocked} and route to \texttt{format\_refusal}.\\
\item
  \textbf{Classify} --- \texttt{nodes/classify.py} labels greeting,
  specification, or question. Specifications lock subspace language for
  later \texttt{filter\_path}.\\
\item
  \textbf{Retrieve} --- \texttt{nodes/retrieve.py} may rewrite
  coreference, apply sticky subspace decay, search KB, merge RRF/CE
  sets, fire entity tools, and evaluate evidence scores. Low evidence
  can refuse or broaden.\\
\item
  \textbf{Clarify or build} --- Ambiguous multi-subspace queries may ask
  a clarifying question via \texttt{generate\_clarification}. Otherwise
  \texttt{build\_context.py} assembles Persian system instructions, up
  to 20 chunks (\texttt{MAX\_CHUNKS}), history (possibly compacted), and
  trimmed entity JSON.\\
\item
  \textbf{Generate} --- \texttt{guarded\_generate} never talks to Gemma
  directly; Guardrails proxies upstream with cleanup of leaked special
  tokens.\\
\item
  \textbf{Format} --- Citations and finish reasons are shaped for the
  OpenAI response schema; audit/timing attach for non-stream responses.
\end{enumerate}

\subsection{Knowledge Base deep dive}\label{knowledge-base-deep-dive}

\textbf{Section summary.} The Work Credit RAG Knowledge Base
(\texttt{components/knowledgebase}, kb-manager) is the retrieval
substrate for Persian credit-scoring Q\&A: it turns heterogeneous source
files into versioned chunks and entity supplements, then answers hybrid
search requests with measurable stage latency. This section walks the
ingest path (parsers → Persian preprocess → semantic chunking →
\texttt{EntityList}), the live retrieval stack (tantivy BM25 + MiniLM
dense + RRF \emph{k}=60 + BGE-m3 rerank), Redis caching, subspace
filters, observed IR quality, and the tip gaps that still affect
orchestrator integration.

\subsubsection{Purpose in the platform}\label{purpose-in-the-platform}

The KB is neither a chat model nor a policy layer. Its contract is
stricter: \emph{given a Persian (or mixed) query and optional subspace
hint, return ranked chunk evidence with timing and citation metadata}.
The orchestrator (\texttt{:8100}) calls \texttt{POST\ /search/api} after
input rails; \texttt{build\_context} then packs hits for guarded
generation. The service listens on \textbf{\texttt{:8000}}, persists via
SQLAlchemy into Postgres + \textbf{pgvector} (SQLite fallback), and
exposes FastAPI routes for search, pipeline, and metrics. Correctness is
IR-first---Hit@\emph{k}, MRR, nDCG---plus \emph{stage\_ms} so
regressions surface as a quality cliff or a named-stage latency spike.

\subsubsection{Ingest pipeline}\label{ingest-pipeline}

\begin{figure}
\centering
\includegraphics{assets/diagrams/07_kb_ingest_hl.png}
\caption{High-level KB ingest}
\end{figure}

\emph{Figure --- High-level ingest.} Source trees under
\texttt{kb-source} enter one pipeline orchestrator that fans into
durable stores: document/chunk tables (with dense embeddings) and a
parallel \texttt{EntityList} table for structured supplements that must
not be flattened into ordinary prose chunks. Ingest is a write-path
concern separate from hybrid read; rebuilds or incremental updates
produce a coherent snapshot for search consumers.

Coordination lives in
\texttt{components/knowledgebase/kb-manager/kb\_manager/pipeline/orchestrator.py}.
\texttt{PipelineOrchestrator} selects a parser by extension
(\texttt{parsers/registry}), runs \texttt{PreprocessingPipeline} for
Persian hygiene (digit/character normalization, punctuation cleanup),
then chunks with \texttt{SemanticChunker} and embeds via the
sentence-transformer embedder. Folder hierarchy under \texttt{kb-source}
becomes \texttt{domain} / \texttt{category} metadata---the later
substrate for \texttt{filter\_path} and sticky subspaces.

\begin{figure}
\centering
\includegraphics{assets/diagrams/08_kb_ingest_detail.png}
\caption{Detailed KB ingest}
\end{figure}

\emph{Figure --- Ingest detail.} The per-file loop is parse → preprocess
→ content-hash skip/update → semantic chunk → embed → store, with an
early branch for supplementary Excel lists. Annex/list paths bypass
normal chunking into \texttt{EntityList} rows; synonym/glossary annexes
feed BM25 synonym resources instead of polluting the chunk corpus.
Embedder wiring on that branch fills \texttt{description\_embedding} for
semantic routing---if the orchestrator is built \emph{without} an
embedder, those vectors stay empty and entity injection silently
degrades.

\texttt{SemanticChunker} (\texttt{kb\_manager/chunker/semantic.py})
prefers meaning-preserving units: tabular schemas become row-aware
chunks with Persian field labels; narrative docs split on structure and
normalized question text. Near-duplicate normalized questions are
deduped so BM25 is not rewarded for FAQ clones.

\paragraph{EntityList model}\label{entitylist-model}

Structured supplements are first-class in
\texttt{components/knowledgebase/kb-manager/kb\_manager/models/database.py}:

\begin{itemize}
\tightlist
\item
  \texttt{EntityList.list\_name} --- human title used as the retrieval
  key surface\\
\item
  \texttt{description} / \texttt{description\_embedding} --- short
  Persian description plus JSON embedding for cosine matching\\
\item
  \texttt{content\_json} --- sheet/row payload kept intact for later
  injection into context
\end{itemize}

This design keeps bank-name tables, code maps, and similar annexes
\emph{queryable as units} instead of scattering cells across MiniLM
space where short keys underperform.

\subsubsection{Retrieval pipeline}\label{retrieval-pipeline}

\begin{figure}
\centering
\includegraphics{assets/diagrams/09_kb_retrieval_hl.png}
\caption{High-level KB retrieval}
\end{figure}

\emph{Figure --- High-level retrieval.} A request hits Redis first
(keyed on normalized query, \texttt{top\_k}, optional keyword boost, and
\texttt{filter\_path}). Hits short-circuit the heavy path; misses run
hybrid retrieve and write back with TTL \textbf{600 s}. The coarse view
explains why warm production traffic can look far faster than a cold
micro-benchmark even when the ranker code path is unchanged.

The authoritative implementation is
\texttt{components/knowledgebase/kb-manager/kb\_manager/web/routes/search.py}.
\texttt{search\_knowledge\_base} builds (or reuses) in-memory indexes
and runs:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Sparse leg} --- Rust \textbf{tantivy} BM25
  (\texttt{tantivy\_bm25.py}), Persian-aware tokenization with character
  3-grams so short keyword queries still overlap.\\
\item
  \textbf{Dense leg} --- \texttt{DenseSemanticIndex} in
  \texttt{dense.py} over \textbf{paraphrase-multilingual-MiniLM-L12-v2}
  (384-d), with vectors served from pgvector HNSW when configured.
  Encoding goes through \texttt{\_encode} / \texttt{\_ensure\_model};
  the private \texttt{\_model} is not a public attribute.\\
\item
  \textbf{Optional HyDE} --- when enabled, an extra dense leg
  contributes another ranked list.\\
\item
  \textbf{Fusion} --- Reciprocal Rank Fusion with constant
  \textbf{\emph{k} = 60}
  (\texttt{rrf\_score\ =\ 1\ /\ (k\ +\ rank\ +\ 1)}), merging sparse and
  dense ranks into a hybrid candidate pool.\\
\item
  \textbf{Rerank} --- cross-encoder
  \textbf{\texttt{BAAI/bge-reranker-v2-m3}} over a large candidate pool
  (env \texttt{KB\_RERANKER\_TOP\_K}, default 100), with optional
  RRF↔rerank score interpolation and BM25-leg guards so dense-only
  dominance cannot bury a strong keyword hit.
\end{enumerate}

\begin{figure}
\centering
\includegraphics{assets/diagrams/10_kb_retrieval_detail.png}
\caption{Detailed KB retrieval}
\end{figure}

\emph{Figure --- Retrieval detail.} Stages that populate
\texttt{SearchSteps.stage\_ms} are named explicitly: \texttt{bm25},
\texttt{dense}, \texttt{hyde}, \texttt{rrf}, \texttt{rerank},
\texttt{build\_context}, and \texttt{total}. The same timings feed
\texttt{metrics.record\_stage\_ms}, so a 20 ms regression can be blamed
on rerank GPU contention versus a BM25 rebuild. \texttt{filter\_path}
prunes \texttt{chunk\_data} before ranking for a subspace token or
slash-separated path, matching ingest folder-hierarchy tags---how sticky
product/domain subspaces work without re-embedding the query.

\paragraph{Redis cache and filters}\label{redis-cache-and-filters}

\texttt{KB\_REDIS\_TTL} defaults to \textbf{600} seconds. Keys are
SHA-256 digests of the normalized query plus \texttt{top\_k}, keyword
boost, and \texttt{filter\_path}, so subspace answers do not leak across
domains. If Redis is down, an in-process memory cache with the same TTL
keeps single-worker use viable; production still prefers Redis for
shared warm results across workers.

\subsubsection{Known tip gaps}\label{known-tip-gaps}

Two tip hazards remain and should not be rediscovered during
orchestrator work.

First, several \texttt{search.py} sites still gate entity encoding with
\texttt{hasattr(dense,\ "model")\ and\ dense.model\ is\ not\ None}.
\texttt{DenseSemanticIndex} keeps the SentenceTransformer on
\textbf{\texttt{\_model}}, so the check is \emph{always false}: entity
inject becomes a \textbf{silent no-op} even when dense search is
healthy. Use \texttt{dense.\_encode({[}...{]})} (or a helper that calls
\texttt{\_ensure\_model}).

Second, the orchestrator expects
\textbf{\texttt{POST\ /search/supplement}}
(\texttt{\{query,\ threshold\}}, default \textasciitilde0.4) to rank
\texttt{EntityList} rows by embedding over \emph{list\_name +
description}. That route is \textbf{missing on tip}; only an
in-\texttt{/search/api} step-8 inject remains, and it is compromised by
the same \texttt{hasattr} bug. Restoring the route and wiring embeddings
through \texttt{\_encode} is required for reliable entity supplements in
production chat turns.

\subsection{Deep dive: Orchestrator}\label{deep-dive-orchestrator}

\textbf{Section summary.} The Work Credit RAG orchestrator is the public
OpenAI-compatible face of the platform (\texttt{:8100}). It does not
embed documents or serve Gemma itself: a compiled LangGraph
(\texttt{RAGState}) validates and classifies each turn, retrieves from
the knowledge base with sticky subspace memory, optionally clarifies
ambiguous credit domains, packs a char-budgeted prompt, and
\emph{always} generates through Guardrails. Sticky
\texttt{filter\_path}, per-subspace evidence floors, entity-list
trimming, and history compaction keep Persian multi-turn chats inside
the 8192-token upstream window while preserving citations for the WebUI.

\subsubsection{Role in the request path}\label{role-in-the-request-path}

Upstream of the graph, Open WebUI (or any OpenAI client) posts to
FastAPI \texttt{create\_app} in
\texttt{components/orchestrator/src/work\_rag\_orchestrator/api.py}. The
API allocates a \texttt{request\_id}, restores prior
\texttt{sticky\_subspace} from the LangGraph checkpointer when the
conversation continues, and invokes the compiled graph. Downstream
dependencies are only KB (\texttt{KB\_BASE\_URL}, default
\texttt{:8000}) and Guardrails (\texttt{GUARDRAILS\_BASE\_URL}, default
\texttt{:8200}). Configuration for thresholds, keyword boosts, and
compaction lives in \texttt{config.py}; the typed carry bag for every
node is \texttt{RAGState} in \texttt{state.py}.

A deliberate invariant of the user-facing path: \textbf{the orchestrator
never opens an HTTP session to Gemma.} \texttt{guarded\_generate} posts
\texttt{prompt\_messages} to Guardrails
\texttt{POST\ /v1/chat/completions}; Guardrails alone dials the loopback
LLM (llama-server or the H200 manager). Input rails also run during
\texttt{validate\_input} via \texttt{/v1/rails/check}. Utility
compaction may call an internal OpenAI-compatible summarizer for rolling
history, but that path is system-generated and separate from answer
generation.

\subsubsection{LangGraph topology}\label{langgraph-topology}

The deterministic graph is assembled in \texttt{graph.py}
(\texttt{create\_graph} / \texttt{compile\_graph} with
\texttt{MemorySaver} for MVP checkpointing):

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{\texttt{validate\_input}} --- extract the latest user query;
  call Guardrails input rails. If \texttt{blocked}, route to
  \texttt{format\_refusal} and end.
\item
  \textbf{\texttt{classify}} --- bucket the turn as \texttt{greeting},
  \texttt{specification}, or \texttt{question}. Greetings and
  product-spec answers short-circuit straight to
  \texttt{format\_response} (no retrieval).
\item
  \textbf{Optional \texttt{hybrid\_classify}} --- when
  \texttt{hybrid\_classifier\_enabled} is true, an SVM-first classifier
  may escalate low-confidence labels before retrieval; otherwise edges
  go directly to \texttt{retrieve}.
\item
  \textbf{\texttt{retrieve}} --- rewrite/coreference as needed, call KB
  hybrid search (and optional supplement), apply sticky or inferred
  subspace filters, entity inject, and evidence gates.
\item
  \textbf{\texttt{should\_clarify}} --- conditional edge: if
  supplemental/injected entities exist, \emph{continue} (dictionary hits
  short-circuit clarification). Else if \texttt{needs\_clarification},
  embedding ambiguity (when routed), or scattered ambiguous queries with
  no \texttt{applied\_subspace}, branch to
  \textbf{\texttt{generate\_clarification}} and end. Otherwise continue.
\item
  \textbf{\texttt{build\_context}} --- number sources, compact history,
  enforce \texttt{prompt\_char\_budget} and \texttt{MAX\_CHUNKS}.
\item
  \textbf{\texttt{guarded\_generate}} --- Guardrails chat completion →
  answer (or content-filter refusal).
\item
  \textbf{\texttt{format\_response}} --- OpenAI-shaped payload plus RAG
  citations and audit fields.
\end{enumerate}

\subsubsection{Sticky subspace, filters, and
evidence}\label{sticky-subspace-filters-and-evidence}

Credit knowledge is partitioned into Persian path labels (cheque report,
facilities for natural/legal persons, general KB). \texttt{filter\_path}
on the request is authoritative: when present, \texttt{retrieve} scopes
\texttt{KnowledgebaseClient.retrieve(...,\ filter\_path=...)} and maps
the path back to a subspace label for badges and thresholds. Separately,
\textbf{\texttt{sticky\_subspace}} persists across turns in checkpointed
state \emph{without} always forcing this turn's
filter---\texttt{state.py} keeps it distinct from
\texttt{applied\_subspace} so the scorer can decide keep versus switch.
The API layer may re-inject sticky scope for generic follow-ups
(pronouns, short ``بله/بیشتر'') while \texttt{sticky\_decay\_turns}
(default 3) drops stale stickiness after consecutive generic turns.

Per-subspace \textbf{evidence floors}
(\texttt{config.get\_evidence\_threshold}) refuse hallucination when top
hybrid/rerank scores are too weak: cheque is lenient (\texttt{0.05}),
facilities\_person \texttt{0.10}, facilities\_legal and general
\texttt{0.15} (global fallback \texttt{evidence\_min\_score=0.15}).
Keyword boosts on filtered KB calls bias BM25 harder for cheque Q\&A
(\texttt{3.5}) than narrative general prose (\texttt{2.5}). Weak
filtered hits can trigger a single whole-KB retry
(\texttt{filter\_path=None}) audited as \texttt{fallback\_used}.

Entity dictionaries (reason codes, shareholders, loan titles) arrive as
\texttt{injected\_entities} / \texttt{supplemental}.
\texttt{trim\_supplemental} keeps at most \textbf{top-3 lists × 4\,KB}
serialized JSON each, ranks rows by query-token hit count, and
\textbf{doubles weight for code-like tokens} (Latin letters or digits
such as \texttt{sbd1}) so exact codes outrank rows that only share the
word «کد». Without this trim, a single reason-code sheet can exceed
100\,KB and overflow the upstream context.

\subsubsection{Context packing and
compaction}\label{context-packing-and-compaction}

\texttt{build\_context.py} caps retrieval evidence at
\textbf{\texttt{MAX\_CHUNKS\ =\ 20}}, prefers lexical matches when
truncating, and respects
\textbf{\texttt{prompt\_char\_budget\ =\ 20000}} characters for the full
generation prompt (system + context + history + question + entity
reserve). Persian can tokenize near \textasciitilde3 chars/token; twenty
thousand characters leave headroom inside an 8192-token Gemma window for
the answer. When estimated tokens exceed
\texttt{compact\_threshold\_tokens} (4500), rolling-summary compaction
replaces older turns while keeping the newest
\texttt{compact\_recent\_turns} verbatim; prior ``not found'' refusals
are stripped so they do not poison a later successful retrieval.

\section{6. Deep Dive: Server Setup \& Model
Serving}\label{deep-dive-server-setup-model-serving}

\subsection{Section summary}\label{section-summary-2}

Work Credit RAG runs on two deliberately different hosts: an
unprivileged Vast.ai RTX 3090 used for integrated MVP bring-up, and a
corporate H200 box (\texttt{ai-gpu1}) that owns production model
serving. The Vast path boots application services from host virtualenvs
via \texttt{deploy/vast/start.sh} and treats Gemma as an external
\texttt{llama-server} on loopback \texttt{:18000}. The H200 path
introduces the LLM Inference Manager on \texttt{:9000} as an
OpenAI-compatible gateway in front of a multi-backend fleet---llama.cpp
Gemma replicas on \texttt{8080–8084}, TensorRT-LLM champion traffic on
\texttt{:8010}, and embedding workers on \texttt{8001–8003}---while
Redis, vector stores, and Open WebUI ride a Docker data plane. Corporate
egress goes through Squid at \texttt{192.168.203.2:3128}, which makes
\texttt{httpx} \texttt{trust\_env=False} on localhost calls a hard
correctness requirement. Containerization is staged
(\texttt{compose.mvp.yml} for privileged compose hosts; parent
\texttt{deploy/docker} plus the server-setup cutover plan for H200).
Capacity planning follows
\texttt{docs/plans/million-user-scale-plan.md}: Kubernetes horizontal
scale-out versus saturating 2×H200 scale-up. Measured generation
throughput on H200 (history \texttt{013}) shows TensorRT-LLM BF16
continuous batching reaching \textasciitilde3874 aggregate tok/s at
concurrency 128 versus a flat \textasciitilde58 tok/s llama.cpp Q4
single-slot path---about \textbf{67×} aggregate under the same Persian
decode workload.

\subsection{Dual hosts: Vast MVP versus H200
production}\label{dual-hosts-vast-mvp-versus-h200-production}

The Vast instance (documented against instance \texttt{50713720}, 1× RTX
3090, \textasciitilde24 GB VRAM) cannot run Docker: the container is
unprivileged, so \texttt{unshare}/iptables fail and
\texttt{compose.mvp.yml} is reserved for privileged or local compose
hosts. Startup order is postgres → Gemma → KB \texttt{:8000} →
guardrails \texttt{:8200} → tracing collector \texttt{:3000} →
orchestrator \texttt{:8100} → Open WebUI \texttt{:13000}, driven by
\texttt{bash\ deploy/vast/start.sh} and torn down with port-scoped
\texttt{deploy/vast/stop.sh} (never \texttt{pkill\ python}). Gemma stays
bound to \texttt{127.0.0.1:18000} with \texttt{-\/-ctx-size\ 8192},
\texttt{-\/-no-mmproj}, \texttt{-\/-jinja}, and
\texttt{chat\_template\_kwargs} that disable thinking tokens; guardrails
point \texttt{UPSTREAM\_LLM\_BASE\_URL} at that loopback OpenAI surface.
HF caches must set both \texttt{HF\_HOME} and \texttt{HF\_HUB\_CACHE}
(typically \texttt{/tmp/hf\_clean}) or hub 1.x resolves an empty phantom
tree. Public reachability is SSH tunnels only; NAT port remapping after
creation is unavailable.

The H200 host is the opposite operational model: Docker is available for
the data plane, Jenkins can act as root, and GPU memory (2× H200 NVL)
supports concurrent backends. Model control plane is the manager on
\texttt{:9000}. Chat backends include five llama.cpp Gemma instances
(\texttt{8080–8084}), optional Qwen on \texttt{:8090}, and the
TensorRT-LLM champion on \texttt{:8010}. Embedding microservices expose
e5 / BGE / MiniLM-style endpoints on \texttt{8001–8003} for KB and
offline tooling. Orchestrator and guardrails still speak OpenAI JSON,
but production generation is intended to go Manager → champion (with
automatic fallback into the llama.cpp pool if \texttt{:8010} is
unhealthy). Figure 13 captures that high-level split---clients to
manager to model backends, with Docker handling
Redis/Qdrant/pgvector/WebUI---while Figure 14 expands the port map and
the orchestrator/guardrails/KB adjacency.

\subsection{Manager OpenAI gateway and Squid
discipline}\label{manager-openai-gateway-and-squid-discipline}

\texttt{components/server-setup/llm\_inference\_manager/app.py} exposes
\texttt{/v1/chat/completions}, \texttt{/v1/completions},
\texttt{/v1/models}, \texttt{/health}, plus admin load/unload and
Triton/TRT promote endpoints. Round-robin counters distribute load
across replica URLs; SQLite (\texttt{manager.db}) records history and
metrics. Every outbound call to localhost backends constructs
\texttt{httpx.AsyncClient(...,\ trust\_env=False)}. That flag is not
stylistic: the host shell exports
\texttt{HTTP\_PROXY}/\texttt{HTTPS\_PROXY} toward Squid
\texttt{http://192.168.203.2:3128} for apt, pip, git, and Hugging Face.
If httpx inherits those variables, loopback requests to \texttt{:8010}
or \texttt{:8080} are sent to Squid, which cannot hairpin them, and
health checks hang or fail opaque timeouts. The same rule appears in
guardrails and observability clients; operators still need
\texttt{no\_proxy}/\texttt{curl\ -\/-noproxy\ \textquotesingle{}*\textquotesingle{}}
for manual probes. Promotion of \texttt{gemma-4-31b} to TRT is an admin
action (\texttt{POST\ /admin/triton/promote?...}) that flips the gateway
mapping without changing orchestrator env vars.

\subsection{Containerization and
cutover}\label{containerization-and-cutover}

Three layers coexist. Root \texttt{compose.mvp.yml} describes a
privileged MVP: containerized postgres/pgvector, Redis, KB, guardrails,
orchestrator, and WebUI, with Gemma remaining \emph{external} on the
host (\texttt{host.docker.internal:18000}). Parent
\texttt{deploy/docker/} holds compose variants
(\texttt{docker-compose.yml}, GPU and Qdrant overlays, nginx) for hosts
that can run the NVIDIA runtime. On H200,
\texttt{components/server-setup/docs/migration/containerization-report.md}
defines a zero-downtime cutover: build images first, validate each
service on alternate ports, run E2E through WebUI against alt backends,
then per-service swap host process → container on the \emph{same}
production port, with host venvs retained for rollback. Final port
identity is frozen (\texttt{8000}, \texttt{8001–8003},
\texttt{8080–8084}, \texttt{8100}, \texttt{8200}, \texttt{9000},
\texttt{13000}, Redis \texttt{16379}, postgres \texttt{5432}, tracing
\texttt{3000}). Phases 1--3 never stop production traffic; only Phase 4
cutover changes listeners.

\subsection{Scaling: million-user plan and measured decode
throughput}\label{scaling-million-user-plan-and-measured-decode-throughput}

\texttt{docs/plans/million-user-scale-plan.md} separates
\textbf{scale-out} from \textbf{scale-up}. Scale-out places stateless
FastAPI/orchestrator pods behind Kubernetes Ingress with HPA on CPU, GPU
inference behind Triton/TensorRT replicas scaled by queue depth (KEDA),
and a dedicated vector cluster (Qdrant) with read replicas---trading
operational complexity for elastic concurrency (Figure 17). Scale-up
keeps a single 2×H200 machine saturated: large in-RAM indexes, many
Triton instance groups per GPU, and Gunicorn worker counts near core
count, minimizing cross-node latency at the cost of vertical coupling
(Figure 18). For Work Credit RAG's Persian chat path, generation---not
retrieval---dominates wall time, so inference batching efficiency
dominates capacity math.

\section{Deep Dive: Guardrails \&
Security}\label{deep-dive-guardrails-security}

\subsection{Section summary}\label{section-summary-3}

Guardrails (\texttt{Work\_RAG-Guardrails}, port \texttt{:8200}) is the
mandatory safety boundary between the LangGraph orchestrator and the
Gemma inference plane. Every user turn is checked on the \emph{input}
stage before retrieval context is answered; every completed assistant
reply is checked again on the \emph{output} stage before it returns to
WebUI. The service no longer embeds NVIDIA NeMo Guardrails. Runtime
policy is a two-layer stack: fast deterministic detectors that emit
\emph{evidence signals}, then an adjudicating judge (\texttt{gemma},
\texttt{mizan}, or \texttt{hybrid}) that must allow or refuse. Judge
timeout, empty verdict, or transport error fails \emph{closed}---the
request is refused rather than passed through. Production refusals are
premade Persian category messages that never leak detector internals;
Iranian PII in allowed answers is masked; secret markers hard-block.

\texttt{rails/check} for input and output stages, then

\subsection{Endpoints and user-facing
policy}\label{endpoints-and-user-facing-policy}

\textbf{\texttt{POST\ /v1/rails/check}} accepts
\texttt{\{stage,\ text,\ request\_id\}} for \texttt{input} or
\texttt{output}. The response carries \texttt{allowed}, \texttt{action},
category ids, and a \texttt{reason} string. In production mode
(\texttt{GUARD\_RESPONSE\_MODE}), \texttt{reason} is a premade Persian
message keyed by category---prompt injection, jailbreak, hate, offense,
out-of-scope, PII, secret, policy---without exposing regex matches or
judge traces. Output-stage hate/profanity refusals blame the
\emph{answer} (``پاسخ حاوی محتوای نامناسب است\ldots{}'') rather than the
user.

\textbf{\texttt{POST\ /v1/chat/completions}} is the OpenAI-compatible
guarded gateway used by the orchestrator's \texttt{guarded\_generate}
node. Flow:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Extract the question slice from an augmented user message
  (\texttt{Question:} / \texttt{سوال:}), cap to the rails text limit.
\item
  Input rails → refuse with \texttt{finish\_reason="content\_filter"} if
  blocked.
\item
  Trim chat history to a Persian-aware char budget so upstream context
  (8192 tokens) is not overflowed.
\item
  Call Gemma with
  \texttt{chat\_template\_kwargs:\ \{"enable\_thinking":\ false\}} and
  strip leaked control tokens.
\item
  Output rails → refuse or continue.
\item
  If Iranian PII validators still match an \emph{allowed} answer,
  \texttt{events.mask\_text} replaces national-id / Sheba / mobile digit
  runs (and API-key-like spans) before return.
\end{enumerate}

Health and readiness expose upstream reachability and policy version;
the interactive dashboard aggregates masked JSONL events (block rate,
categories, 24h timeline, sample viewer).

\subsection{Upstream contract details}\label{upstream-contract-details}

All outbound \texttt{httpx.AsyncClient} calls to \texttt{:18000} /
\texttt{:9000} set \textbf{\texttt{trust\_env=False}}. Without that
flag, a host Squid \texttt{HTTP\_PROXY} can hang loopback traffic and
stall generation.

Upstream context overflow and other Gemma failures used to surface as
pydantic validation crashes when the code emitted
\texttt{finish\_reason="error"} (not in the OpenAI-compatible literal).
The gateway now maps timeout and overflow paths to
\textbf{\texttt{finish\_reason="length"}} with a short Persian retry
hint---never an internal 500 and never a leaked token-budget body.
Successful rails refusals use \texttt{content\_filter}; clean answers
use \texttt{stop}.

\subsection{Known gaps}\label{known-gaps}

\textbf{Streaming.} When \texttt{stream=true}, input rails still run,
then tokens are forwarded from upstream SSE (or chunked from a buffered
JSON body). The live stream path does \emph{not} reassemble the full
assistant text for output rails or append a complete output-stage JSONL
event the way non-streaming \texttt{guarded\_completion} does. Operators
should treat streaming as latency-first and keep production WebUI on
buffered completions until output rails are applied post-stream.

\textbf{\texttt{Observability} class unwired.} \texttt{observability.py}
defines a Phase-4 helper that would attach \texttt{request\_id},
triggered rules, risk scores, and latency to responses, but nothing in
\texttt{service.py} or \texttt{judge.py} imports it. Live telemetry
today is the masked \texttt{events} JSONL plus the dashboard---not the
richer risk-scorer envelope.

\subsubsection{\texorpdfstring{8.2 Knowledge-base \texttt{stage\_ms} and
Redis}{8.2 Knowledge-base stage\_ms and Redis}}\label{knowledge-base-stage_ms-and-redis}

Every successful \texttt{POST\ /search/api} response includes a
\texttt{stage\_ms} object written in
\texttt{kb\_manager/web/routes/search.py} as each leg finishes: BM25
(tantivy RAM index), dense MiniLM encode + HNSW/pgvector lookup,
Reciprocal Rank Fusion (\texttt{k=60}), BGE-m3 cross-encoder rerank, and
\texttt{total}. The same object is stored with the cached SearchSteps
payload under Redis (\texttt{KB\_REDIS\_TTL}, default \textbf{600s}) or
an in-memory fallback when Redis is down; exact-cache hits typically
return in \textbf{2--7 ms} and never cache error responses. Operators
can therefore diagnose ``dense vs rerank'' without attaching a
profiler---\texttt{jq\ \textquotesingle{}.stage\_ms\textquotesingle{}}
on a warm curl is the day-to-day tool.

\subsubsection{\texorpdfstring{8.3 Orchestrator timings, AuditTrail, and
\texttt{ORCH\_DEBUG}}{8.3 Orchestrator timings, AuditTrail, and ORCH\_DEBUG}}\label{orchestrator-timings-audittrail-and-orch_debug}

Graph nodes call \texttt{record\_timing(state,\ stage,\ elapsed\_ms)}
(\texttt{state.py}) so retrieve, clarify, \texttt{build\_context},
\texttt{guarded\_generate}, format, and retry/broaden paths accumulate
into \texttt{state{[}"stage\_timing\_ms"{]}}. On the
\textbf{non-streaming} OpenAI chat path, \texttt{api.py} builds a
Pydantic \texttt{AuditTrail} that copies those timings together with
retrieved chunks, guard signals, context preview, subspace ambiguity
fields, and wall \texttt{latency\_ms}. Setting \texttt{ORCH\_DEBUG=1}
turns on app-level INFO logging (uvicorn alone would otherwise silence
the package logger) and enables opt-in context diagnostics inside
\texttt{build\_context} so engineers can verify what actually reached
Gemma without redeploying.

\textbf{Streaming caveat.} The SSE branch streams tokens from Guardrails
→ Gemma and finalizes citations/metadata, but it does \textbf{not}
assemble the full \texttt{AuditTrail} save path used by the buffered
branch. Traces still update, yet operators relying on audit-complete
JSON for offline review will under-collect streaming traffic.

\subsubsection{8.4 Langfuse v2 HTTP and host
fallbacks}\label{langfuse-v2-http-and-host-fallbacks}

\texttt{work\_rag\_orchestrator/tracing.py} prefers direct HTTP to
Langfuse v2: envelopes carry top-level \texttt{id} + ISO
\texttt{timestamp}, and updates re-\texttt{trace-create} the same id (v2
has no \texttt{trace-update}). Posts are submitted on a small thread
pool with short timeouts so tracing never blocks the request loop. When
the real UI at \texttt{:3001} is unavailable, the same path targets the
parent \texttt{components/tracing} collector on \texttt{:3000}, which
appends to \texttt{/tmp/langfuse\_traces.jsonl} and exposes a minimal
Langfuse-compatible ingestion + \texttt{/observe} timeline UI.

Separately, \texttt{eval\_store.py} persists enriched pipeline cards to
\textbf{\texttt{/tmp/observability.db}} (WAL SQLite,
\texttt{EVAL\_DB\_PATH}) and mirrors them to
\textbf{\texttt{/tmp/pipeline\_traces.jsonl}} (\texttt{TRACE\_JSONL}).
The observability dashboard router under \texttt{/api/observability} is
how Studio/WebUI-side tooling can push ratings and stage cards into that
store.

\subsubsection{8.5 Guard events, manager metrics, and retrieval
DLQ}\label{guard-events-manager-metrics-and-retrieval-dlq}

Guardrails write terminated/allowed decisions to
\texttt{/tmp/guard\_events.jsonl} (\texttt{GUARD\_EVENTS\_FILE}) with
digit-run PII masking, and serve aggregates on the Persian dashboard at
\texttt{http://127.0.0.1:8200/dashboard}. On the model plane,
\texttt{llm\_inference\_manager} keeps session, message, and latency
rows in \texttt{manager.db} and surfaces KB \texttt{stage\_ms}
breakdowns when a manager-side search probe is used. When filtered
retrieval returns empty (or fails after fallbacks), orchestrator
\texttt{retrieve.py} appends a record to
\texttt{/tmp/dlq\_retrieval.jsonl} so empty-hit regressions remain
greppable after the fact.

\subsubsection{8.8 Optimizations that moved the
numbers}\label{optimizations-that-moved-the-numbers}

\begin{itemize}
\tightlist
\item
  \textbf{RAM-first tantivy + HNSW.} Rust tantivy BM25 (≈50 MB heap,
  RAMDirectory) and RAM-pinned dense/pgvector HNSW remove cold disk
  seeks from the hot path; startup pre-warm loads indexes and CUDA
  kernels before the first user query.
\item
  \textbf{RRF then selective rerank.} Fusion at \texttt{k=60} keeps
  candidate quality high while the cross-encoder scores a bounded pool
  (GPU, pool 30)---cheap legs stay cheap.
\item
  \textbf{Entity / context trim.} Orchestrator supplemental injection is
  capped (top-3 × \textasciitilde4 KB) and
  \texttt{prompt\_char\_budget≈20k} / \texttt{MAX\_CHUNKS=20} protect
  the Gemma \textbf{8192} context window from overflow (upstream
  overflow is surfaced as \texttt{finish\_reason=length}, not a hard
  500).
\item
  \textbf{TRT champion serving.} On H200, TensorRT-LLM Gemma remains the
  throughput champion versus llama.cpp Q4 for concurrent decode; Vast

  concurrency, not with KB \texttt{stage\_ms}.
\end{itemize}
